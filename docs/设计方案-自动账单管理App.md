# 手机自动账单管理 App —— 完整设计方案

> 工作代号：**「自动账本」**
> 目标：让用户不手动记账，App 自动采集手机上所有消费记录并自动归类，形成可视化账单与消费分析。
> **范围决策**：本版本仅做 **Android**，iOS 因系统限制暂缓（如后续需要可走"快捷指令截屏 + 导入"半自动路线，见附录 A）。

---

## 一、产品概述

### 1.1 一句话定位

一款**自动采集、自动分类、隐私优先**的手机记账应用——支付完成后账单自动生成，无需用户手动输入。

### 1.2 核心价值

| 痛点 | 本产品的解法 |
|------|-------------|
| 手动记账坚持不下来 | 支付通知/短信自动入库，零操作 |
| 记了账不知道钱花哪儿了 | 自动多级分类 + 可视化报表 |
| 担心财务隐私泄露 | 本地加密优先，云同步端到端加密，可完全离线使用 |
| 多平台账单分散（支付宝/微信/银行卡） | 统一采集、去重合并到一个账本 |

### 1.3 目标用户

- **主力人群**：20–40 岁都市上班族、学生——消费频次高、渠道多、没耐心手动记。
- **次级人群**：家庭财务管理者——希望汇总家庭成员共同支出。
- **特征**：手机支付占消费 90% 以上；对隐私有一定敏感度；希望"低成本掌控财务"。

## 二、竞品简析与差异化

| 竞品 | 自动化程度 | 差异化机会 |
|------|-----------|-----------|
| 随手记 / 鲨鱼记账 | 以手动记账为主，有短信导入但非实时 | 我们主打**实时自动采集**，用户零操作 |
| MoneyWiz / 财禅 | 功能全但贵、上手门槛高 | 我们做**轻量、免费、自动化** |
| 银行/支付宝自带账单 | 只有单一渠道数据，分类粗糙 | 我们**跨渠道聚合 + 智能分类** |
| Timi 记账 | 设计好但手动 | 我们**自动化 + 隐私本地化** |

**核心差异化**：`自动化采集 × 跨渠道去重合并 × 端上智能分类 × 本地加密`。

## 三、功能架构

### 3.1 功能总览（分层）

```
┌─────────────────────────────────────────────────┐
│ 表现层：首页 / 报表 / 预算 / 日历 / 设置          │
├─────────────────────────────────────────────────┤
│ 数据层：本地加密存储 · 云同步(可选) · 导入导出     │
├─────────────────────────────────────────────────┤
│ 处理层：去重合并 · 自动分类 · 汇率换算 · 统计      │
├─────────────────────────────────────────────────┤
│ 采集层：通知监听 · 短信解析 · 账单导入 · 手动补录  │
└─────────────────────────────────────────────────┘
```

### 3.2 采集层——如何"自动"拿到消费记录

#### Android 端（能力较完整）

| 渠道 | 技术方案 | 采集内容 | 优先级 |
|------|---------|---------|--------|
| **通知监听** | `NotificationListenerService`，用户授权后监听支付宝/微信/银行App的支付通知 | 商户名、金额、时间 | ★★★ 主渠道 |
| **短信解析** | `READ_SMS` 权限，匹配银行扣款短信模板 | 银行卡尾号、金额、商户、余额 | ★★★ 主渠道（国内） |
| **账单文件导入** | 支付宝/微信/银行 App 导出的 CSV/XLSX，App 内导入并解析 | 全量历史账单 | ★★ 补充历史 |
| **无障碍服务**（可选增强） | `AccessibilityService` 读取支付成功页 | 精确商户与金额 | ★ 可选，合规敏感 |
| **手动记账** | 普通手动录入 + 语音/拍照小票 OCR | 兜底 | 补充 |

#### iOS 端（系统限制，走"半自动"路线）

| 渠道 | 技术方案 | 说明 |
|------|---------|------|
| **快捷指令自动化** | 引导用户创建 Shortcuts：当打开支付宝/微信时自动截屏 → App 通过 `App Intent` 拿到截图 → 端上 OCR 提取金额/商户 | 近实时 |
| **账单文件导入** | 同 Android，Files App 导入 CSV | 补全历史 |
| **手动/语音记账** | Siri Shortcut 快速记账 | 兜底 |
| **订阅账单转发** | 用户将账单邮件转发到专属邮箱，App 解析 | 信用卡用户 |

> **渠道优先级策略**：同一笔交易多渠道命中时（如银行短信 + 支付宝通知都出现），按 `渠道信任度 + 时间窗口` 去重合并，保留信息最全的一条。

### 3.3 处理层——自动分类引擎（核心）

#### 多级类目体系

```
一级类目（10 个）          二级类目（示例）
├── 餐饮                  外卖 / 堂食 / 咖啡奶茶 / 零食
├── 交通                  打车 / 公交地铁 / 加油 / 停车
├── 购物                  日用百货 / 服装 / 数码 / 美妆
├── 居住                  房租 / 水电燃气 / 物业 / 宽带
├── 娱乐                  视频会员 / 游戏 / 电影 / 旅游
├── 医疗                  药品 / 门诊 / 体检
├── 教育                  课程 / 书籍 / 培训
├── 人情                  红包 / 礼物 / 请客
├── 金融                  信用卡还款 / 理财 / 转账 / 手续费
└── 其他                  兜底类目
```

#### 分类 Pipeline（三级漏斗）

```
原始消息 ──▶ ① 预处理 ──▶ ② 规则命中 ──▶ ③ 模型预测 ──▶ 置信度判定
             商户名归一化    内置商户库+      端上文本分类     ≥0.85 自动入库
             (去广告词/     用户自定义规则   (fastText/      0.6–0.85 入库但标记
              统一大小写)    (regex → 类目)   MiniLM 蒸馏)    "待确认"
                                                          <0.6 归入"其他"
                                                          并在日报中提示
```

**冷启动方案**：内置 3000+ 常见商户映射库（美团→餐饮外卖、滴滴→交通打车、京东→购物、链家→居住……）+ 各渠道关键词规则表，开箱即准确率 ≥ 85%。

**持续学习**：用户手动修改分类后，本地写入 `merchant → category` 映射（下次自动命中），并作为训练样本用于端上模型微调（可选）。

### 3.4 表现层——核心页面

| 页面 | 核心内容 |
|------|---------|
| **首页** | 今日/本周/本月消费总览卡片、最近交易流水（下拉即见）、快捷手动记一笔 |
| **报表** | 月度饼图、分类趋势折线、周/月/年对比、消费热力日历 |
| **预算** | 月总预算 + 分类预算，进度条与超支推送提醒 |
| **账单日历** | 日历视图查看每天消费明细 |
| **渠道中心** | 各采集渠道的连接状态、授权管理、重新同步 |
| **设置** | 类目管理、规则自定义、隐私开关、数据导出/清空、生物识别锁 |

**交互亮点**：支付完成后 2 秒内，App 可选弹出一条**轻量通知**："✓ 已记录：美团外卖 ¥35.80（餐饮-外卖）"，点错可一键改类。

## 四、技术架构

### 4.1 客户端

| 项 | 选型 | 理由 |
|----|------|------|
| 框架 | **Flutter**（Dart） | 一套代码覆盖 Android + iOS，UI 性能接近原生 |
| 原生桥接 | Platform Channels | 调用 Android 通知监听/短信读取、iOS Shortcuts/OCR |
| 本地数据库 | **SQLite + SQLCipher**（drift/Isar 封装） | 全库 AES-256 加密，支持复杂报表查询 |
| 端上 ML | TensorFlow Lite / ML Kit | 文本分类模型端上推理，无需联网 |
| OCR | iOS: VisionKit；Android: ML Kit | 小票/截图提取金额与商户 |
| 状态管理 | Riverpod | 可测试、类型安全 |

### 4.2 后端（可选——MVP 可纯本地，云服务用于同步与匿名统计）

```
Flutter App ──HTTPS/TLS──▶ API Gateway (Go/Rust)
                            │
                            ├── Sync Service（端到端加密账本同步）
                            │     └ PostgreSQL（只存密文 blob）
                            ├── Push Service（预算提醒/周报推送）
                            └── 匿名统计（可选关闭）
                                  └ ClickHouse（脱敏分类统计，改进内置商户库）
```

**E2EE 同步方案**（参考 Standard Notes 模式）：
- 用户密钥派生自账户密码（Argon2id），服务器永远只见密文。
- 同步以"操作日志"形式上传加密事件流，各端重放得到一致状态。
- 用户可随时在设置中**彻底删除云端数据**（GDPR/个保法合规）。

### 4.3 核心数据模型

```sql
-- 交易流水（核心表）
CREATE TABLE transactions (
  id            TEXT PRIMARY KEY,       -- UUID
  amount        INTEGER NOT NULL,       -- 分为单位，避免浮点
  currency      TEXT DEFAULT 'CNY',
  occurred_at   INTEGER NOT NULL,       -- Unix 秒
  merchant_raw  TEXT,                   -- 原始商户描述
  merchant_norm TEXT,                   -- 归一化后
  category_id   TEXT REFERENCES categories(id),
  account_id    TEXT REFERENCES accounts(id),
  source        TEXT NOT NULL,          -- notification|sms|import|manual
  raw_hash      TEXT NOT NULL,          -- 原始消息指纹，用于去重
  confidence    REAL,                   -- 分类置信度
  confirmed     INTEGER DEFAULT 0,      -- 用户是否确认过
  note          TEXT,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

-- 类目
CREATE TABLE categories (
  id        TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES categories(id),
  name      TEXT NOT NULL,
  icon      TEXT,
  sort      INTEGER DEFAULT 0
);

-- 账户/渠道
CREATE TABLE accounts (
  id       TEXT PRIMARY KEY,
  type     TEXT NOT NULL,     -- alipay|wechat|bank|cash|credit
  name     TEXT NOT NULL,
  color    TEXT
);

-- 用户自定义/内置分类规则
CREATE TABLE rules (
  id          TEXT PRIMARY KEY,
  pattern     TEXT NOT NULL,  -- regex 或关键词
  category_id TEXT REFERENCES categories(id),
  priority    INTEGER DEFAULT 0,
  builtin     INTEGER DEFAULT 0
);

-- 预算
CREATE TABLE budgets (
  id          TEXT PRIMARY KEY,
  period      TEXT NOT NULL,   -- '2026-09' 或 'monthly'
  category_id TEXT,
  amount      INTEGER NOT NULL
);
```

## 五、安全与隐私设计（重中之重）

| 原则 | 落地措施 |
|------|---------|
| **最小权限** | 只申请 `READ_SMS` / `NotificationListener` 等必要权限；短信解析后**不保留原文**，只保留结构化结果 |
| **本地优先** | 所有数据默认只存本地加密数据库；云同步为可选功能，且默认关闭 |
| **端到端加密** | 云端只存密文，密钥不出设备（Argon2id 派生） |
| **生物识别锁** | 打开 App 需指纹/面容解锁 |
| **透明可审计** | 设置中提供"数据流水线"页面：展示每条记录来源渠道与原始消息摘要 |
| **数据可携带/可删除** | 一键导出 CSV/JSON；一键本地+云端彻底删除 |
| **合规** | 遵循《个人信息保护法》、工信部 App 治理要求；上架 Google Play 需提交 SMS 权限使用声明（核心功能审查）；应用商店隐私政策完整披露 |

> **关键设计决策**：App 绝不上传原始短信或通知内容——解析全部在设备端完成，仅结构化结果（金额/商户/时间）入本地库。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Google Play 限制 `READ_SMS` | 无法上架海外商店 | 国内分发为主；海外版仅用通知监听 + 导入 |
| 银行短信格式多变、新增银行 | 解析漏单 | 模板热更新 + 用户自定义模板 + 未识别消息队列提示 |
| 支付宝/微信无个人开放 API | 无法拉取全量账单 | 通知监听为准；月度 CSV 导入补历史；关注开放平台动态 |
| iOS 系统封闭 | 无法做到全自动 | 明确"半自动"定位：快捷指令 + 导入；诚实告知用户预期 |
| 用户隐私信任 | 使用门槛 | 本地优先 + 隐私仪表盘 + 可选开源核心 |
| 分类不准 | 体验差 | 规则库持续运营 + 用户反馈学习 + "待确认"队列 |

## 十、总结：一页话术

> **自动账本**：付完款，账单就自动记好了。
> 我们通过监听支付通知和解析银行短信，在 2 秒内自动生成交易记录，并用端上智能引擎自动归类到餐饮/交通/购物等类目。所有数据默认存在手机本地加密数据库，不联网也能用；云同步采用端到端加密，隐私完全由用户掌控。MVP 聚焦 Android 端跑通"采集→分类→报表"闭环，6–8 周上线。

## 附录 A：采集方案全量对比与低内存架构

### A.1 采集/识别方案全量对比

| 方案 | 触发机制 | 稳态内存 | 实时性 | 覆盖率 | 优点 | 缺点 | 建议定位 |
|------|---------|---------|--------|--------|------|------|---------|
| **通知监听** `NotificationListenerService` | 系统事件回调，无常驻轮询 | ≈0 常驻（事件期 15–30MB，空闲即被回收） | 秒级 | 高（支付宝/微信/银行 App 均发通知） | 全渠道覆盖、格式较稳定、权限易获取 | 个别 App 通知内容简略 | ★★★ 主渠道 |
| **短信广播** `SMS_RECEIVED` | 系统广播唤醒，瞬时 | ≈0 常驻（事件期 10–20MB） | 秒级 | 中（银行卡扣款短信） | 银行卡渠道权威补充 | 短信模板需持续维护 | ★★★ 主渠道（国内） |
| **账单邮件解析** | 用户在支付宝/银行开启"月账单发送至邮箱"，App 用 IMAP/OAuth 拉取 | ≈0（WorkManager 每日一次按需拉取） | 天/月级 | 中（历史全量） | 官方数据、适合历史补账与对账 | 不实时、需用户配置邮箱 | ★★ 历史补全 |
| **银联开放平台授权查询** | 用户授权后 REST API 拉取银行卡交易 | ≈0（按需 HTTP） | 天级 | 高（银行卡全覆盖） | 官方权威数据、准确率 100% | 需银联/银行开放资质 | ★★ 有资质后升级 |
| **无障碍读支付页** `AccessibilityService` | 监听界面变化 | 30–60MB 常驻 | 秒级 | 高 | 实时最准、可拿到页面级商户名 | 用户感知强、合规与省电敏感 | ★ 可选增强开关 |
| **截屏 + OCR**（iOS 快捷指令 / Android 检测打开支付 App 后截屏） | Shortcuts 自动化 / UsageStats 触发 | 按需（前台瞬时） | 分钟级 | 中 | iOS 主力方案；无后台常驻 | 设置门槛、OCR 偶有误差 | iOS 主渠道 / Android 补充 |
| **分享面板 Share Target** | 用户把支付截图分享给 App | 0 | 手动 | 兜底 | 零学习成本、无权限要求 | 手动操作 | 兜底 |
| **VPN 本地流量分析** `VpnService` | 捕获支付域名网络流量 | 40–80MB 常驻 | 实时 | 高 | 技术上最全面 | 合规风险大、耗电、复杂 | 不建议 |

> **结论**：主渠道保持「通知监听 + 短信广播」双事件驱动（均无常驻轮询）；低内存场景下补充「账单邮件解析」和「银联开放平台授权拉取」这两个**按需拉取**方案——它们不占用任何常驻内存，适合历史补全与权威对账。

### A.2 低内存架构：事件驱动 + 双进程隔离

```
┌─────────────────────────────────────────────────────┐
│  :collector 轻量进程（纯 Kotlin，不加载 Flutter 引擎） │
│                                                     │
│  · NotificationListenerService 回调（系统绑定管理）    │
│  · SMS BroadcastReceiver（广播唤醒，瞬时）             │
│  · 原生正则解析 → raw_hash 去重 → SQLCipher 直接写入   │
│  · 可选：轻量通知反馈"已记录 ¥xx"                      │
│                                                     │
│  稳态内存 ≈ 15–30MB，空闲即被系统回收                  │
│  事件到来时由系统拉起，无轮询、无前台服务、无心跳        │
├─────────────────────────────────────────────────────┤
│  主进程（Flutter UI，仅用户打开 App 时启动）            │
│                                                     │
│  · 首页首帧查 SQLite：occurred_at 索引 LIMIT 20        │
│  · 报表/预算/设置页面按需懒加载                        │
│  · 列表虚拟化：内存中仅保留可视范围 + 缓冲              │
├─────────────────────────────────────────────────────┤
│  WorkManager（系统调度，独立于进程存活）               │
│                                                     │
│  · 每日拉取账单邮件（IMAP）                           │
│  · 云同步增量合并（若开启）                           │
│  · 银行短信模板热更新                                 │
└─────────────────────────────────────────────────────┘
```

**关键设计点**

1. **采集进程不加载 Flutter/WebView**：通知和短信解析全部在原生 Kotlin 层用正则完成，避免 Flutter 引擎（80–150MB）在后台被拉起。
2. **不常驻前台服务**：`NotificationListenerService` 由系统绑定管理，内存紧张时系统可回收进程，事件到来时自动重新绑定——用户无感知。
3. **SQLite WAL 模式**：`:collector` 进程写、主进程读，双进程并发安全，无需 IPC。
4. **突发事件防抖**：短时间大量通知（如双十一）先 append 到轻量队列文件，再批量解析入库，避免 CPU 唤醒风暴。
5. **双进程内存预算**：

| 组件 | 稳态内存 | 活跃时机 |
|------|---------|---------|
| `:collector` 进程 | 15–30MB | 仅事件到达时；空闲可被系统回收 |
| Flutter 主进程 | 80–150MB | 仅用户打开 App 时 |
| WorkManager 任务 | ≈0 | 系统定时触发（每日/按需） |
| **后台常驻合计** | **≈ 0**（`NotificationListenerService` 绑定不等于常驻前台） | — |

### A.3 "下次打开自动加载最近支付记录"——本地优先实现

核心思路：**后台采集器在你打开 App 之前就把数据写好了**，打开时只需要查本地库，天然秒开。

```
用户付完款
  → :collector 进程 2 秒内解析并写入加密 SQLite（带 occurred_at 索引）

用户打开 App（可能是 1 小时后、1 天后、甚至 1 周后）
  → Flutter 引擎启动
  → 首页首帧执行：
      SELECT * FROM transactions
      ORDER BY occurred_at DESC
      LIMIT 20;
    （命中索引，< 10ms）
  → 先渲染骨架屏 → 数据填充 → 完成
  → 无任何网络等待
```

**增强体验（可选）**

|------|------|

| 云同步增量合并 | WorkManager 后台静默同步；打开时本地数据立即显示，远端增量后台合并 |
| 1×1 桌面小组件 | 常显"最近一笔：美团外卖 ¥35.80"，不打开 App 也能看 |
| 通知栏常驻摘要（可选） | 类似"今日已消费 ¥128"，点开进 App——同样无常驻服务 |

## 附录 B：真·全自动采集方案（零截图，Android 可执行）

### B.1 可行性结论

| 平台 | 能否"零截图、全自动、读取所有支付" | 原因 |
|------|----------------------------------|------|
| **Android** | **✅ 可以** | 无障碍服务（AccessibilityService）可直接读取其他 App 的界面文本内容，配合通知监听 + 短信广播，三引擎覆盖所有支付路径 |
| **iOS** | ❌ 不可能 | 系统沙盒隔离，第三方 App 无法读取其他 App 的界面内容、数据库或通知；不越狱的前提下截屏 OCR 是唯一半自动手段 |

### B.2 三引擎采集架构

```
┌──────────────────────────────────────────────────────────────┐
│              :collector 轻量进程（纯 Kotlin 原生）              │
│                                                              │
│  引擎① 通知监听（NotificationListenerService）                 │
│  · 支付宝/微信/银行/京东/美团… 所有 App 的支付成功通知            │
│  · 到达即捕获，秒级实时，事件驱动零常驻                          │
│  · 覆盖率 ≈ 95%（绝大多数支付都会发通知）                        │
│                                                              │
│  引擎② 短信广播（SMS BroadcastReceiver）                      │
│  · 银行卡扣款/到账/还款短信                                    │
│  · 覆盖 NFC 交通、刷卡、无 App 通知的场景                       │
│                                                              │
│  引擎③ 无障碍服务（AccessibilityService）★ 核心               │
│  · 直接读取其他 App 界面上的文本节点（非截图、非 OCR）            │
│  · 检测支付成功页："支付成功 ¥35.80 美团外卖"                    │
│  · 检测账单列表页：遍历历史交易行，补全引擎①漏掉的                │
│  · 用户打开支付 App 时自动触发，后台零消耗                      │
│                                                              │
│  ──────────────────────────────────────────────              │
│  统一管道：解析 → raw_hash 去重 → 归类 → 写 SQLCipher           │
│  三引擎输出合并后，同一笔交易只保留信息最全的一条                  │
└──────────────────────────────────────────────────────────────┘
```

**为什么三引擎 = 全覆盖**

| 支付场景 | 引擎①通知 | 引擎②短信 | 引擎③无障碍 | 是否覆盖 |
|---------|----------|----------|-----------|---------|
| 支付宝扫码/付款 | ✓（"付款成功"通知） | — | 兜底 | ✅ |
| 微信支付/转账/红包 | ✓ | — | 兜底 | ✅ |
| 银行卡快捷支付 | 银行 App 通知 | ✓ 银行短信 | — | ✅ 双保险 |
| NFC 刷公交/门禁 | 部分银行通知 | ✓ | — | ✅ |
| 京东/美团/抖音内购 | ✓ App 内通知 | — | ✓ | ✅ |
| 极少数无通知场景 | ✗ | ✗ | ✓（用户打开 App 时读账单页补全） | ✅ |

> 结论：支付发生瞬间由引擎①/②实时捕获；用户任何时间打开支付 App，引擎③自动扫描账单页做兜底对账——两条路径叠加后**覆盖率 ≈ 100%**。

### B.3 无障碍引擎实现细节

#### 工作原理

Android `AccessibilityService` 允许 App 订阅系统级界面事件。当用户在任何 App 中切换页面或内容变化时，系统回调 App，并提供当前界面的 **UI 节点树**（每个节点的文本、ID、位置）。我们的引擎只做一件事：**在这棵节点树里找支付相关的文本并解析**——不截图、不 OCR、无像素操作。

#### 核心代码骨架（Kotlin）

            }
        }

## 附录 C：三引擎去重机制与无感体验设计

### C.1 去重：三引擎不会重复计算

#### 冲突场景示例

用绑定招行卡的支付宝付款 35.80 元，三引擎同时捕获：

```
引擎① 支付宝通知："付款成功 ¥35.80 美团外卖"
引擎② 招行短信：  "您尾号1234的卡于09-16 14:32支出35.80元（美团）"
引擎③ 无障碍：    用户稍后打开支付宝账单页，读到同一笔
```

→ 三条原始消息，但**只会入库一条交易记录**。

#### 三级去重漏斗

```
原始消息 A / B / C
    │
    ▼
① 精确去重（消息级，防系统重复推送）
   raw_hash = SHA256(归一化后的完整文本)
   SQLite UNIQUE 索引 → 写入冲突直接丢弃
   覆盖：同一条通知被系统重新投递、广播重放等
    │
    ▼
② 跨渠道模糊合并（交易级，防多渠道重复）
   匹配窗口：|time_A − time_B| ≤ 120 秒
   匹配条件：金额精确相等（分为单位，无浮点误差）
   渠道配对规则表：
     alipay_notification ↔ bank_sms           → 同一笔（绑卡支付）
     wechat_notification ↔ bank_sms           → 同一笔
     alipay_notification ↔ accessibility_bill → 同一笔（兜底扫描）
     bank_sms ↔ bank_app_notification         → 同一笔
   合并策略：保留信息最全的一条为主记录（有商户名 > 只有金额），
   其余写 merged_into = 主记录 ID，不物理删除（可审计/可回溯）
    │
    ▼
③ 无障碍账单扫描兜底去重（历史级）
   引擎③读到账单列表行 (商户, 金额, 日期)
   → 查本地库：同金额 + 同日期 ±1天 + 商户归一化相似
   → 已存在 → 跳过；不存在 → 新增
```

#### 合并时机

| 阶段 | 机制 | 延迟 |
|------|------|------|
| 实时窗口合并 | `:collector` 进程内存中维护 120 秒滑动窗口，同金额+配对渠道到达即合并 | 0–2 秒 |
| 兜底批量合并 | WorkManager 每 5 分钟扫描 `pending_merge` 队列，处理跨窗口边界 | ≤ 5 分钟 |
| 无障碍扫描去重 | 读账单行 → 实时查库比对 → 只插新增 | 实时 |
| UI 读取 | 只查 `merged_into IS NULL` 的主记录 | 用户永远看不到重复 |

#### 数据模型补充

```sql
ALTER TABLE transactions ADD COLUMN merged_into TEXT REFERENCES transactions(id);
ALTER TABLE transactions ADD COLUMN channels TEXT;  -- 如 "notification,sms"
CREATE UNIQUE INDEX idx_raw_hash ON transactions(raw_hash);
CREATE INDEX idx_merge_lookup ON transactions(amount, occurred_at);
```

### C.2 无感体验设计：让用户忘记 App 的存在

**设计原则：采集静默、反馈环境化、纠错异步化。**

用户全程唯一主动行为 = **想看账单时打开 App**。其余一切都是静默后台。

#### 具体策略

| 层面 | 无感设计 | 用户感受 |
|------|---------|---------|
| **采集** | 三引擎全自动，无弹窗、无确认框、无"已记录"通知 | 付款后什么都没发生 |
| **分类** | 置信度 ≥ 0.85 自动归类不打扰；< 0.6 的攒起来 | 从未被问"这笔是什么" |
| **低置信度处理** | 每周一次批量摘要推送："本周有 3 笔待确认"，点开一次处理完 | 每周最多被打扰一次 |
| **纠错** | 报表页长按改类目 → 规则库自动学习 → 同类下次自动修正 | 改一次就永远对了 |
| **环境反馈（可选）** | 1×1 桌面小组件常显"今日 ¥128 · 本月 ¥3,420"；下拉通知栏才见的低优先级常驻卡片"今日已记 12 笔" | 不打开 App 也能瞥一眼，但不弹横幅 |
| **系统集成** | 快捷设置磁贴一键查看今日消费；桌面小组件点击直达首页 | 想看时一秒到达 |
| **超支提醒** | 只在预算超支时推送（有意义才打扰），平时零推送 | 通知栏永远干净 |

#### 对比"有感"方案

| 打扰行为 | 本产品做法 |
|---------|-----------|
| 每笔支付弹"已记录 ✓"确认 | 默认关闭；可在设置开启（适合刚开始建立信任期） |
| 每笔低置信度交易实时弹窗问类目 | 攒到周报批量处理 |
| 每日推送消费日报 | 默认关闭；只有超支/异常才推 |
| 要求用户定期打开 App 同步 | 后台 WorkManager 静默同步，打开即最新 |

> **信任建立期策略**：前 7 天可开启轻通知（"✓ 已记录 ¥35.80"）让用户确认在正常工作；7 天后默认切换为全静默模式——用户已经信任了，就不需要再看。
